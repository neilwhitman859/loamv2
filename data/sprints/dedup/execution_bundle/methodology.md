# Methodology — Sprint 6 Producer Dedup

This document explains **how** the 493 dedup decisions in this bundle were
reached. The decisions themselves are in `verdict_ledger.jsonl`.

## The problem

The `producers` table contained ~33,281 rows after the LWIN backbone import.
A significant fraction of these were duplicates of the same real-world producer:
accent variants, orthographic differences, country-split rows for the same
global brand, generational succession of family estates, merchant-prefixed
rows, and so on. Loam's product value depends on one row per producer.

## Identity rules

The decision framework is in `docs/IDENTITY_RULES.md` §11 (Producer Identity
Rules). The one-line version:

> **A producer is the brand printed on the label.** Two producer rows MERGE if
> a shopper holding bottles from each row would see the same brand identity on
> the front label. They SKIP if the brand identities differ and there is no
> ownership relation. They are PARENT-CHILD when the brands differ but one
> owns or legally contains the other.

§11.4 enumerates the edge cases (accent variants, generational succession,
JV labels, corporate holdcos, second wines, etc.). §11.4 was amended in B6.6
to codify nine additional patterns that surfaced during Chrome validation
(§11.4.m through §11.4.s — see `docs/IDENTITY_RULES.md` for full text).

## The dedup pipeline

The pipeline operates on producer-pair candidates generated by trigram-based
blocking (~600K pairs). Each pair is classified by a tiered AI ladder, then
the uncertain ones escalate to Chrome-per-pair validation.

### Blocking (B6.3)

For each producer, find candidate duplicates via pg_trgm similarity search on
normalized producer names, joined by country. This produced ~600K pairs across
8 active strategies (exact-normalized, alphanumeric, first-N-tokens, etc.).

### L1 Haiku (B6.3)

Haiku 4.5 classifies each pair as MERGE / SKIP / PARENT_CHILD / UNCERTAIN with
a basic prompt (no rich context). 151K pairs run at $0.052¢/pair. Output has
~99% MERGE precision at confidence ≥0.85 in calibration, but ~5% PC precision
(PC verdicts are noise at L1).

### L1.5 Gemini basic

Gemini 2.5 Flash basic prompt, same pairs, 0.023¢/pair. Serves as a
cross-family cross-check: errors from Haiku and Gemini don't overlap much
(Haiku is cautious, Gemini is aggressive).

### Stage 1 routing

- If L1+L1.5 both MERGE ≥ 0.88 → auto-MERGE candidate
- If L1+L1.5 both SKIP ≥ 0.95 → auto-SKIP
- Otherwise → escalate to Stage 2

### L2 Haiku rich + L2.5 Gemini rich

Both models run with rich prompts that include TTB fingerprint + wine catalog
overlap for each side. ~57K pairs escalated.

### Stage 2 routing

- Both MERGE ≥ 0.90 → auto-MERGE candidate (but validated with L3 web before
  execution)
- Both SKIP ≥ 0.93 → auto-SKIP
- Otherwise → escalate to Stage 3 (Chrome validation)

### Chrome-per-pair validation (B6.5a)

**This is the primary source of the verdicts in this ledger.** Approximately
450 pairs — the pairs most likely to need nuanced judgment — were validated
via Claude-in-Chrome MCP. A human-facing producer-identity analyst (Claude
session) loaded both producer rows' wine lists, then performed per-pair web
searches (DuckDuckGo, Wine-Searcher, importer sites, Jasper Morris, Robert
Parker) to confirm the producer identity and assign the correct verdict.

Every verdict was logged to `data/sprints/dedup/chrome_validation/` with
evidence URLs. The four JSONL files (`yellow_verdicts.jsonl`,
`core_verdicts.jsonl`, `mid_verdicts.jsonl`, `tail_verdicts.jsonl`) total 493
pairs — the scope of this ledger.

### B6.6 amendments + re-Chrome

B6.6 did two things:

1. **Codified §11.4 amendments**: the Chrome validation surfaced nine pattern
   clusters beyond what §11.4.a–l covered originally. §11.4.m (shared-surname
   split), §11.4.n (multi-country global brand), §11.4.o (JV/collab at dedup
   time), §11.4.p (merchant/retailer prefix), §11.4.q (Hospices de Beaune
   pattern), §11.4.r (moved-from §11.4.f: négociant + estate), and §11.4.s
   (sub-brand under parent) were added.

2. **Re-Chromed the verdicts**: the parent Claude session manually validated
   4 pairs it flagged as potentially concerning, then delegated full re-Chrome
   passes to subagents for all 66 Core MERGE+PC pairs and all 127 Mid+Tail+Yellow
   MERGE+PC pairs. The re-Chrome flip rate was ~18% on Core — meaning 18% of
   B6.5a verdicts were wrong or had wrong direction. Most flips were over-eager
   MERGEs on generic shared-surname names (Beausejour, Boisson, Moreau, Jolivet,
   Chalk Hill) that turned out to be unrelated estates in different regions.

All B6.6 overrides are recorded in `rechrome_flips.md` with chrome_url evidence.

## Canonical-row redirect logic

During B6.6 review, an important failure mode surfaced: Chrome validators
often chose a `survivor_name` (MERGE) or `parent_name` (PC) that happens to
already exist as a separate canonical row in the DB, but they didn't know
that. Example:

- Pair proposes "Coche Boulicault → Fabien Coche" (rename-on-merge)
- Chrome picks survivor by §11.6 heuristic (larger wine count)
- Execute script renames that row to "Fabien Coche"
- But a `Fabien Coche` row with 38 wines already exists — now we have two

The ledger resolves this via **canonical-row lookup**: when the final
survivor_name or parent_name matches an existing producer row (same normalized
name, same country) that isn't either side of the pair, the ledger records a
`canonical_redirect_id` pointing at that existing row. The execute script
uses this redirect to merge both pair rows INTO the canonical, rather than
creating a duplicate.

## Verdict vocabulary

| Verdict | Meaning | DB effect |
|---------|---------|-----------|
| `MERGE` | Two rows are the same producer | Re-point all FKs to survivor, soft-delete loser, `producer_merge_history` row |
| `PARENT_CHILD` | Distinct brands, one owns the other | Set child's `parent_producer_id` to parent |
| `SKIP` | Distinct unrelated producers | No-op |
| `KEEP_AS_IS` | Yellow-tier only: the row is fine, no action needed | No-op |
| `DEFERRED_SPRINT_7` | Pair needs more investigation than Sprint 6 can provide | No-op this sprint; flagged for Sprint 7 |

## Survivor selection

Per `docs/IDENTITY_RULES.md` §11.6 the survivor is chosen by:
1. Label-form preference (accent, current canonical form)
2. Metadata completeness
3. Wine count
4. LWIN external_id presence
5. Earliest `created_at`

The canonical-row redirect logic (above) overrides this when an existing
canonical row is found outside the pair.

## Reversibility

Every MERGE execution writes a full JSONB snapshot of the loser row to
`producer_merge_history` before soft-deleting it. A PARENT_CHILD action is
trivially reversible by setting `parent_producer_id = NULL`. The execute
script does not hard-delete any producer row.

See `reversibility.md` for the undo procedure.

## What this bundle does cover (updated 2026-04-20)

Per user directive, the bundle includes **all dedup decisions** surfaced by
Sprint 6, split into two phases:

### Phase 1 — Chrome-validated (fully reviewed)

493 pairs in `verdict_ledger.jsonl`, produced by:
- B6.5a Chrome-per-pair validation (original verdicts in `chrome_validation/*_verdicts.jsonl`)
- B6.6 re-Chrome override (29 FLIP_TO_SKIP + 1 FLIP_DIRECTION + 2 FLIP_TO_MERGE
  + 1 FLIP_TO_PC + 5 NEEDS_HUMAN_REVIEW + 155 KEEP)

These are ready for execution after user testing. The execute script
resolves them with canonical-row redirect, union-find chain resolution, and
§11.6 survivor selection.

### Phase 2 — pipeline auto-decided (not Chrome-validated)

151,150 decisions in `producer_dedup_routing_stage3`, split:
- **146,471 SKIP-family decisions** — no-ops
- **3,939 auto-apply mutations** — 3,154 MERGE + 785 PC
- **740 user-review queue items** — need human judgment before execution

Phase 2 is packaged for external review in `phase2_actionable_decisions.jsonl`
(4,679 rows: 3,939 auto-apply + 740 review-queue) and
`phase2_skip_sample.jsonl` (500-row random sample of the 146,435 SKIPs for
spot-checking).

**Critical:** Phase 2 auto-apply MERGEs have plausible 3-10% flip rate
(extrapolated from Phase 1 Chrome rigor on easier cases). Before execution,
a sampled Chrome audit is recommended. See `phase2_risk_analysis.md`.

## What this bundle does NOT cover

- Wine dedup (same wine across multiple wine rows). That's Sprint 7 scope.
- Re-enrichment of affected producers (prompt v2 work). That's Sprint 8 scope.
- Schema changes for multi-parent collaborations (DVO case). Flagged for
  Sprint 7 in `open_questions.md`.
- Generic-château per-wine re-splitting (Beausejour-style row dumpsters).
  Flagged in `open_questions.md`.

## Why do this at all

Loam's value prop is structured, trustworthy, connected wine data. Producer
dedup is infrastructure for that: one producer = one page = one consistent
view. Duplicates split wine counts, scatter metadata, and break the user's
trust. Sprint 6 is the first major dedup pass since the LWIN import.

## Why not more automation

The first B6.5a Chrome pass was rigorous by design. B6.6's re-Chrome was a
meta-check: can we trust the rigorous pass? Answer: mostly yes, but the tail
has genuine ambiguity that only human judgment resolves. 18% flip rate on
the hardest pairs means more automation wouldn't have helped — the failure
modes were factual, not model-behavior. The right response is to execute the
high-confidence decisions and defer the uncertain ones, not to invent a
super-model that solves what Wine-Searcher, Vivino, CellarTracker, and
Jancis Robinson have all failed to solve in 20+ years of trying.
