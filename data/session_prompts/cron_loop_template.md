# Cron Loop Session Template

Lessons learned from the 2026-04-06 overnight loop (27 cycles, 3 tracks).
Use this as a starting pattern for any future automated cron loop.

---

## Phase 0: Pre-Flight (BEFORE creating the cron)

**0. Read the journal.** Check `data/stats/cron_loop_journal.md` for what
previous loops attempted, what worked, what was wasted, and what backlog remains.
Don't repeat dead-end work.

**1. Gap analysis — prove the work exists.** Before defining any track, query
the DB to measure what's actually available. Don't assume — prove it:

```sql
-- Example: "Are there un-promoted prices in source X?"
SELECT count(*) FROM source_X
WHERE canonical_wine_id IS NOT NULL
AND NOT EXISTS (
  SELECT 1 FROM wine_vintage_prices p
  WHERE p.wine_id = source_X.canonical_wine_id
  AND p.merchant_name = 'X'
);
```

If the answer is 0, don't include that source. The 2026-04-06 loop ran
batch_matcher + retail_promote for 10 sources and got ~0 new prices. A 5-minute
gap query would have skipped the entire track.

**2. Single-focus beats multi-track.** Pick ONE high-value track with a
genuinely large backlog. Don't spread across tracks that are already done.

**3. Size the work.** Estimate how many cycles the track needs. If < 5, just
do it interactively — a cron loop has overhead that isn't worth it for small jobs.

**4. Build the manifest.** Write an explicit numbered list of exactly what each
cycle will do. Don't make the AI figure out "what's next" — that requires
cross-cycle state tracking and is fragile. Example:

```
## Manifest (generated by pre-flight)
Cycle 1:  Gevrey-Chambertin 1er Crus (26 climats, CDC on disk)
Cycle 2:  Nuits-Saint-Georges 1er Crus (41 climats, CDC on disk)
Cycle 3:  Beaune 1er Crus (42 climats, CDC on disk)
...
Cycle 26: Chablis 1er Crus (40 climats, CDC on disk)
Cycle 27: Barolo MGAs (170 MGAs, disciplinare on disk)
Cycle 28: Alsace Grand Crus (51, from appellations table)
```

The manifest makes the loop deterministic. The AI executes item N, not "figure
out what hasn't been done yet." Include the expected count so you can verify.

## Phase 1: Loop Prompt Structure

```
### SELF-TERMINATION CHECK (start of EVERY cycle)
1. Read the manifest. What cycle am I on?
2. If all manifest items are done → cancel the cron, report final summary, STOP.

### CYCLE N
1. Read docs/PRINCIPLES.md and CLAUDE.md (accuracy-first, conservative).
2. Query current state and report.
3. Execute manifest item N.
4. Verify: count matches expected? If not, investigate and report.
5. Append one-liner to cycle log (see below).
6. Re-query stats. Report deltas.
```

---

## Phase 2: Cycle-Level Logging

At the END of each cycle, append a one-liner to the journal's cycle log. This
gives you a per-cycle audit trail without bloating the context:

```
## Run 2 Cycle Log
| Cycle | Item | Expected | Actual | Notes |
|-------|------|----------|--------|-------|
| 1 | Gevrey-Chambertin | 26 | 26 | Clean |
| 2 | Nuits-Saint-Georges | 41 | 41 | Clean |
| 3 | Beaune | 42 | 41 | 1 slug conflict, disambiguated |
```

When something goes wrong at cycle 14, you can see exactly what happened.

## Critical Design Rules

**Self-termination is mandatory.** The loop MUST check done criteria at the
START of each cycle and cancel itself when done. The 2026-04-06 loop kept firing
after completion because it lacked this check.

**Manifest-driven, not exploration-driven.** The pre-flight builds the manifest.
The loop executes it. No "figure out what's next" logic inside the loop.

**No blind retries.** If a script errors, log it and move on. Errors need human
judgment.

**Sequential, not parallel.** batch_matcher and any DB-writing scripts run one
at a time. Supabase connection pooling can't handle concurrent writes.

**Conservative always.** NULL > wrong data. ON CONFLICT DO NOTHING. Verify
counts after every INSERT. If unsure, skip and report why.

## Anti-Patterns (from experience)

| Anti-Pattern | What Happened | Better Approach |
|---|---|---|
| Multi-track when 2/3 tracks are exhausted | Tracks A and C returned 0 from cycle 1 | Gap analysis upfront, drop empty tracks |
| Mechanically running every source | 10 batch_matcher runs produced ~0 new matches | Query gaps first, skip covered sources |
| No self-termination | Cron fired 3x after completion | Check done criteria at cycle start |
| Rotating 6 sweeps that all return 0 | 6 sweeps × multiple cycles = wasted time | Run all 6 once, drop any that return 0 |
| Running batch_matcher unattended | It can crash, has source quirks | Better as interactive work |

## Good Use Cases for Cron Loops

- Seeding vineyards from legal sources (large backlog, one village at a time)
- Seeding appellation_rules from legal sources (same pattern)
- Processing a queue of downloaded PDFs (fetch → extract → insert)
- Any task where: (a) there are 10+ independent units, (b) each unit is
  self-contained, (c) each unit creates genuinely new data

## Bad Use Cases for Cron Loops

- Re-running promotion scripts that have already been run
- Data quality sweeps that were already executed in prior sessions
- Anything requiring interactive judgment (fuzzy matching, error triage)
- Small backlogs (< 5 units) — just do it directly
